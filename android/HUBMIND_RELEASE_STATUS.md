## Signing configuration

`android/app/build.gradle.kts` supports a dedicated release keystore using:

- `HUBMIND_RELEASE_STORE_FILE`
- `HUBMIND_RELEASE_STORE_PASSWORD`
- `HUBMIND_RELEASE_KEY_ALIAS`
- `HUBMIND_RELEASE_KEY_PASSWORD`

The CI workflow decodes `ANDROID_RELEASE_KEYSTORE_BASE64` into the runner's temporary directory and sets `HUBMIND_RELEASE_STORE_FILE`. It accesses release signing secrets only for a push to `main` or an explicitly requested production workflow run—not for pull-request builds.

## Release pipeline

1. CI builds/tests the debug variant and builds the release variant only when signing secrets are available.
2. CI verifies APK package/version metadata and prints the signing certificate fingerprint.
3. With signing secrets configured, CI publishes a stable GitHub Release containing the production-signed APK.
4. The same job calculates SHA-256 and updates `public/api/app-version.json` with the release's direct URL and checksum.
5. The website's Android Updates tab reads the published APK assets from GitHub Releases. The in-app updater uses the updated manifest and verifies the checksum before installation.
6. Without signing secrets, CI publishes only a labelled debug test prerelease; the update manifest remains `NOT_PUBLISHED`.

See [HUBMIND_PRIVATE_APK_RELEASE.md](HUBMIND_PRIVATE_APK_RELEASE.md) for keystore generation, GitHub secret configuration, the workflow dispatch steps, and first-install migration notes.

## First production install warning

A debug-signed installation cannot be upgraded in place with a production-signed APK signed by a new key. Back up/sync important data, uninstall the debug build if necessary, and install the production build fresh. All later production updates must retain the same keystore.
